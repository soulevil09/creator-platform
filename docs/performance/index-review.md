# DB index review (Session 12, D7)

Query-driven: every hot path below is listed with the `where` / `orderBy`
shape the code actually issues (file references are to `apps/api/src/`) and
the index that serves it, or **none** with the reason that is acceptable.
Indexes were added **only** where a row here names the read path that pays
for their write cost. Migration: `apps/api/prisma/migrations/20260927120000_security_index_review`.

Legend: **PK** = primary key · **UQ** = unique index · **new** = added by
the Session 12 migration.

## Changes in the migration

| Id  | Change                                                                                                                            | Justified by | Why                                                                                                                                                                                                                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | **Add** `AuditLog_traceCode_idx` on `(("metadata"->>'traceCode')) WHERE "action" IN ('content.served','generation.image_served')` | #27          | Closes the Session 09 Open Item: the lookup was a sequential scan of the whole audit table. Partial, so the one index `AuditLog` gains covers only the two serve actions — the rows that carry a code.                                            |
| I2  | **Add** `ReferenceImage_modelProfileId_idx`                                                                                       | #18, #23     | Postgres does not index foreign keys on its own; every generation request loads a profile's images by this FK. Write-rare table (≤10 rows per model).                                                                                             |
| I3  | **Add** partial `GenerationJob_cleanup_expiresAt_idx` on `("expiresAt") WHERE status='COMPLETED' AND "storageKey" IS NOT NULL`    | #20          | COMPLETED is the bulk of the table; without it the daily sweep scans every job. Rows leave the index when the sweep nulls their key.                                                                                                              |
| I4  | **Add** partial `Content_cleanup_pending_idx` on `("id") WHERE "deletedAt" IS NOT NULL AND "storageKey" IS NOT NULL`              | #19          | Soft-deleted-but-not-yet-purged content is normally empty or tiny; indexing it by `id` serves the keyset walk directly instead of scanning the catalogue.                                                                                         |
| D1  | **Drop** `ContentAccess_contentId_idx`                                                                                            | #4, #13      | Pure duplicate: `ContentAccess_contentId_userId_key` is a btree on `("contentId","userId")`, and a btree's leading column serves every `contentId`-only lookup the dropped single-column index could. One fewer index to maintain on every grant. |

Expression/partial indexes are raw SQL in the migration with a matching
comment in `schema.prisma` (Prisma has no primitive for them — same pattern as
`GenerationJob_one_pending_per_subscriber`).

**Querying the trace index.** Use raw SQL with exactly the indexed expression
and predicate, as in row #27. Prisma's JSON `path` filter compiles to
`metadata #>> '{traceCode}'`, which is a different expression and will not use
`AuditLog_traceCode_idx`.

## Reviewed and left alone

- `Subscription_status_idx` is the leading column of the non-unique
  `Subscription_status_cancelAtPeriodEnd_currentPeriodEnd_idx`, so it is
  probably redundant. It is not a duplicate of a **unique** constraint's
  leading column (the spec's bar for dropping), so it stays; it is a
  candidate for a later cleanup once real query plans exist.
- `GenerationJob_modelId_idx` is unused today (kept by Session 08 for the
  deferred credit-spend revenue share, Session 12.5).
- `CREATE INDEX` (not `CONCURRENTLY`) takes a short write lock. Prisma runs a
  migration in a transaction, where `CONCURRENTLY` is not allowed, and every
  table involved is small at MVP. A large-table index later should be a
  hand-run `CREATE INDEX CONCURRENTLY`.

## Findings not fixed here (out of this session's scope)

- **F1 — content list loads a model's whole catalogue, with an N+1.**
  `listModelContent` (`content/content.service.ts:282`) issues `findMany` with
  no `take`, then calls `resolveAccess` for every row — one
  `contentAccess.findUnique` per STANDARD/PREMIUM row for a logged-in
  non-owner — and only then paginates in memory. Fine for MVP-sized
  catalogues. A model with thousands of items needs DB-side pagination
  (`take`/keyset on `createdAt`, at which point a `(modelId, createdAt)` index
  pays for itself) and one batched `contentAccess.findMany {userId, contentId
in}` per page.
