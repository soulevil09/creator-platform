# Session 08 — AI Image Personalization

## Context Recap (from CLAUDE.md)

- **Consent & likeness data already exist (Session 03):** `ModelProfile.aiConsent` / `aiConsentAt` (boolean opt-in) and `ReferenceImage` (up to 10 per model, S3 `storageKey` only, signed URL minted on demand, never persisted) are live in the schema. This session is the first to *read* them for a real purpose.
- **Storage & watermarking discipline (Session 04):** `StorageClient` (`uploadFile` / `getObject` / `getSignedUrl` / `deleteFile`, S3-compatible) and the injectable `ImageProcessor` (`sharp`-backed `watermark`) are wired into `buildServer` like the emailer — tests inject fakes, nothing touches sharp's native binary or real S3 in CI. Content is watermarked **on-the-fly at serve time**, never stored pre-watermarked. Reuse both verbatim.
- **Credit wallet already exists (Session 05):** `CreditWallet.balance` is a plain `Int` ("credits", not minor currency units). `walletService.debitCredits` / `addCredits` accept an optional transaction client; a debit is a conditional `updateMany({ where: { userId, balance: { gte: amount } } })` that throws `InsufficientCreditsError` (402) having mutated nothing on failure. Reuse this service directly — do not reimplement debit logic.
- **Provider-swappable architecture is the house style (Sessions 05/06):** every external integration ships as `IXxxProvider` + a real adapter + a `MockXxxProvider`, selected in a `provider.factory.ts` that memoises per instance and crashes at boot (`assertXxxProviderConfigured()`) on a bad env value — never silently falls back. Follow this exact shape for AI generation: `IAIProvider` / `ReplicateAdapter` / `MockAIProvider` / `provider.factory.ts`.
- **Neither merchant/API account needs to be live to build this session** — Woovi, NOWPayments, and Paxum were all implemented and fully tested against `nock`-mocked HTTP before any of those accounts were approved, with "verify against a live sandbox" logged as an Open Item. Do the same here: build and test `ReplicateAdapter` against mocked HTTP; live verification against a real Replicate token is a follow-up, not a blocker.
- **Credit-pack revenue currently has no per-model attribution** (`PaymentTransaction.modelShareCents` is `null` for `CREDIT_PACK` rows, by design — see Open Items) because nothing generated by a credit spend has ever carried a `modelId`. This session's generation record **must** carry `modelId`, precisely so a future session can extend revenue-sharing to credit spend without a data migration. Implementing that revenue share is explicitly **out of scope** for Session 08.
- **Live re-check discipline (Session 07):** gating flags that can change after the fact (there: `Subscription.status`; here: `ModelProfile.aiConsent`) must be read fresh at the moment of the gated action, never cached from an earlier step.

## Objective

Let a subscriber spend credits to generate an AI-personalized image of a specific model, using either a **preset** (hair/clothing/pose/scenario) or a **custom text prompt**, while the model's actual likeness is anchored behind a **hidden system prompt** the subscriber never sees, sends, or can override. Debit is credit-based only — **no active subscription is required**, matching the Revenue Model table (subscriptions and credit spend are independent revenue flows).

---

## Product Decisions (locked for this session)

1. **Generation is synchronous.** The API call blocks on the Replicate provider call and returns the finished (or failed) result in the same HTTP response. No job queue, no polling endpoint, no WebSocket notification.
2. **Automatic refund on provider failure.** If the Replicate call itself fails or times out, the already-debited credits are refunded in the same request before responding. Refund does **not** apply to requests rejected for content-safety reasons (see below) — those are rejected *before* any credit is touched, so there is nothing to refund.
3. **Generated images are retained with an expiration**, not permanent and not one-time-view. Default retention: 30 days from completion (`GENERATION_IMAGE_RETENTION_DAYS`, tunable). Past `expiresAt`, the image is no longer servable (404/410) even though the storage object may still physically exist — actual object deletion is a cleanup job, explicitly deferred (see Open Items note to add).

## Deliverables & Acceptance Criteria

### 1. Prisma schema

- `GenerationMode` enum: `PRESET | CUSTOM`
- `GenerationStatus` enum: `PENDING | COMPLETED | FAILED`
- `GenerationJob` model:
  - `id`, `subscriberId` (→ `User`), `modelId` (→ `User`) — **required, non-null**, this is the field the future revenue-share work depends on
  - `mode: GenerationMode`, `presetId: String?` (PRESET only), `userPrompt: String?` (the subscriber-supplied text only — CUSTOM mode, or a preset's human-readable label for audit; **never** the resolved hidden anchor prompt)
  - `creditsCost: Int`
  - `status: GenerationStatus @default(PENDING)`
  - `storageKey: String?` — nullable until `COMPLETED`; same "never serialized to a client" treatment as `Content.storageKey` / `Message.attachmentStorageKey`
  - `providerJobId: String?` (Replicate prediction id, for audit/debug only)
  - `errorMessage: String?` (FAILED only — a short internal-facing message, never the raw provider payload)
  - `expiresAt: DateTime?` — set only on `COMPLETED`
  - `createdAt`, `updatedAt`
  - Indexes: `@@index([subscriberId, createdAt])` (gallery list), `@@index([modelId])` (future revenue-share query path, unused today but cheap to add now vs. a migration later)
- **Acceptance:** migration generated **and applied** to Supabase (`cd apps/api && npx prisma migrate deploy` — see Session 07's tooling note on why `cd apps/api` first). `prisma migrate status` reports all prior migrations plus this one applied.

### 2. `IAIProvider` abstraction (`modules/generation/provider.interface.ts`)

```
IAIProvider
  ├── generateImage(params: {
  │     anchorPrompt: string,          // hidden, server-built, never logged in full at info level
  │     userPrompt: string | null,     // subscriber's own text, empty for pure presets
  │     referenceImageUrls: string[],  // short-TTL signed URLs of the model's ReferenceImages
  │   }) → { imageBuffer: Buffer, providerJobId: string }
  └── (throws AIProviderError on any failure — timeout, rejected content, HTTP error — normalized so the caller doesn't need to know Replicate's shape)
```

- `ReplicateAdapter implements IAIProvider` — briefly justify the specific Replicate SDXL model/version chosen (pin an exact version hash, not `latest`); it must accept image conditioning (e.g. an img2img or IP-Adapter-style SDXL variant) since **text alone cannot anchor a specific person's likeness** — a pure text-to-image SDXL call does not satisfy the "prevents drift" requirement in the platform brief. Creates a prediction, polls its status endpoint until `succeeded`/`failed` within a bounded budget (`GENERATION_TIMEOUT_MS`, default 90000ms); exceeding the budget is treated as a failure (cancel the prediction if the API supports it, otherwise just stop polling and fail closed).
- `MockAIProvider implements IAIProvider` — deterministic, zero HTTP, returns a small fixed placeholder image buffer; used in tests and via `AI_PROVIDER=mock`.
- `provider.factory.ts` — `getAIProvider()` reads `AI_PROVIDER` (`replicate | mock`), memoises, throws `AIProviderConfigError` on an unknown value; `assertAIProviderConfigured()` runs in `buildServer` so a typo crashes at boot, matching Sessions 05/06.
- **Acceptance:** `ReplicateAdapter` tested against `nock`-mocked HTTP for success, provider-error, and timeout paths — no real network call in the test suite (mirrors the Session 05/06 nock discipline exactly).

### 3. Likeness anchor engine (`modules/generation/anchor.ts`)

- A pure function `buildAnchorPrompt(modelProfile, referenceImageSignedUrls): { anchorPrompt: string, referenceImageUrls: string[] }` that assembles the hidden system prompt from the model's profile + reference images. This value is **never** returned in any API response, never included in `GenerationJob.userPrompt`, and never written to a log line above debug level.
- **Acceptance:** a dedicated unit test asserts that no API response body, error message, or non-debug log output anywhere in the module contains the anchor prompt string.

### 4. Content-safety gate — **non-negotiable, checked before any credit is touched**

This runs on **every** CUSTOM prompt and blocks it with `400 { error: 'prompt_rejected' }` before `walletService.debitCredits` is ever called:

- **Reject any prompt indicating a minor** — age-related terms, school-uniform/childlike descriptors, and similar signals. This check cannot be disabled by any env var or role, including admin.
- **Reject any prompt naming or clearly targeting a real person other than the model being personalized** (celebrities, public figures, or anyone by name) — the platform's standing principle is that AI personalization only ever uses a likeness the model her/himself has explicitly opted into; extending it to a third party without their consent is out of scope, full stop.
- Whichever Replicate model is selected, if it exposes a `disable_safety_checker`-style flag for general nudity (needed, since this is a consented adult platform), **the age/minor filter above is this platform's own responsibility and stays active regardless of what the provider's flag does.**
- Every rejection is written to `AuditLog` (new action, e.g. `generation.prompt_rejected`) with the prompt hash (not the raw prompt) for abuse-pattern review, not the prompt itself in plaintext.
- **Acceptance:** integration tests cover at least one case per rejection category, asserting `400` and zero wallet/DB side effects (no `GenerationJob` row created, no credits touched).

### 5. Endpoints (`modules/generation/generation.routes.ts`)

- `GET /api/generations/presets` — public or `authenticate`-only (your call, justify); returns the server-side preset catalog (`id`, `label`, `creditsCost`) from `@creator-platform/shared`. **Client never supplies a cost — it is always resolved server-side from this catalog**, same discipline as `SUBSCRIPTION_PLANS`/`CREDIT_PACKS` in Session 05.
- `POST /api/generations` — `authenticate` + `authorize('subscriber')`, body `{ modelId, mode: 'preset' | 'custom', presetId?, customPrompt? }`:
  1. 404 if `modelId` doesn't resolve to a `MODEL` with a `ModelProfile`.
  2. **Live** check `modelProfile.aiConsent === true` (fresh read, never cached) → 403 `ai_not_enabled` otherwise.
  3. Resolve cost server-side (`presetId` lookup or `GENERATION_CUSTOM_PROMPT_COST`); 400 on an unknown `presetId` or a `mode: 'custom'` with no `customPrompt`.
  4. Run the content-safety gate (Deliverable 4) on `customPrompt` when present — reject before anything else happens.
  5. Reject with `429` if the caller already has a `PENDING` `GenerationJob` (one in-flight generation per user at a time — see Performance Requirements).
  6. `walletService.debitCredits(userId, cost)` → 402 `insufficient_credits` on failure, nothing else happens.
  7. Create `GenerationJob` row `PENDING` with `modelId`, `mode`, `presetId`/`userPrompt`, `creditsCost`.
  8. Mint short-TTL signed URLs for the model's `ReferenceImage`s, build the anchor prompt (Deliverable 3), call `IAIProvider.generateImage(...)`.
  9. **On success:** store the raw (unwatermarked) image via `StorageClient.uploadFile` at `generations/{subscriberId}/{cuid}.{ext}`; update the job to `COMPLETED` with `storageKey`, `providerJobId`, `expiresAt = now + GENERATION_IMAGE_RETENTION_DAYS`; respond `201` with the job id + a signed URL to the (to-be-watermarked-on-serve) image.
  10. **On failure/timeout:** `walletService.addCredits(userId, cost)` (refund), update the job to `FAILED` with a short internal `errorMessage`, write an `AuditLog` row, respond `502 generation_failed`. The refund and the status update happen in the same transaction so a crash between them cannot leave credits gone with no job to show for it.
- `GET /api/generations` — `authenticate` + `authorize('subscriber')`, cursor-paginated, caller's own jobs only (`subscriberId` from JWT), thumbnails as signed URLs only for `COMPLETED` jobs with `expiresAt` in the future.
- `GET /api/generations/:id` — owner-only, **404 not 403** for a non-owner (same enumeration-resistance pattern as Session 06's payout detail and Session 07's conversation history) and also 404 once `expiresAt` has passed even for the owner (the object may still exist in storage, but it is not "there" from the API's perspective).
- `GET /api/generations/:id/image` — owner-only, 404 rules identical to above; streams the image **watermarked on-the-fly**, reusing Session 04's `ImageProcessor.watermark` verbatim, `Cache-Control: no-store`, `storageKey` never serialized anywhere in this module.

## Security Requirements

- Content-safety gate (Deliverable 4) runs before any DB write or credit debit, with no bypass for any role.
- Anchor prompt is never serialized, logged above debug, or reachable through any endpoint (Deliverable 3's test enforces this).
- `modelId`/`aiConsent` are always server-resolved and live-checked; a client cannot generate against a model who has revoked consent since onboarding.
- `storageKey` follows the existing "never leaves the service" rule from Sessions 03/04/07.
- Cost is always resolved from the server-side catalog; a client-supplied cost value, if sent, is ignored (same rule as Session 05 checkout).
- Rate limit `POST /api/generations` (suggest 10/hour/user — justify your number) in addition to the one-in-flight-per-user rule in Deliverable 5, step 5 — a blocking call to an external provider is exactly the kind of endpoint a client could otherwise use to hold open many concurrent connections.
- `AI_PROVIDER_API_KEY` follows the existing `env.ts` eager-validation pattern — missing value crashes at boot when `AI_PROVIDER=replicate`.

## Performance Requirements

- The synchronous provider call is I/O-bound (awaited), so it does not block Fastify's event loop, but it does hold one connection open for the duration — bound it with `GENERATION_TIMEOUT_MS` and fail closed past that budget.
- One in-flight `GenerationJob` per subscriber at a time (Deliverable 5, step 5) bounds worst-case concurrent open connections per user to 1, independent of the rate limit.
- `GET /api/generations` list query must not N+1 (a single `findMany`, signed URLs minted in parallel like Session 03/04's list endpoints).
